# kernd: single-binary VPS dashboard daemon

This change adds `kernd`, a ~4600-line C daemon that manages kern app deployments from a single binary. It implements an admin web UI with session-based auth, a SQLite-backed app registry, a git-clone-and-build deploy worker (pthread), a fork/exec process manager, a host-header-based reverse proxy (libuv TCP), cgroup v2 resource isolation with graceful fallback, pipe-based log capture with 10MB rotation, and tar.gz backups with age-based pruning. The daemon integrates into the existing CMake build and links against libkern for its HTTP server, router, sessions, config parser, and database layers.

Watch for: Command injection in the deploy worker via unsanitized `system()` calls (confirmed). XSS in admin page action URLs where app names are interpolated without escaping (confirmed). Proxy connection memory leak — `proxy_conn_t` is never freed (confirmed). Admin dashboard served over plaintext HTTP on port 8443 with no TLS (confirmed). Deploy worker accesses SQLite from a detached pthread while the main loop may also write, with no serialization (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The deploy worker shells out to `git clone` and the user-supplied `build_cmd` through `system()` with single-quote wrapping that does not escape embedded quotes. An attacker who controls the `repo_url` or `build_cmd` field (submitted via the admin form) can execute arbitrary commands as the daemon's user. The same pattern recurs in `kernd_backup.c` with the tar command.

The reverse proxy buffers only the first 8KB of a request before routing, then stops reading from the client — large POST bodies are silently truncated. More critically, the `proxy_conn_t` struct is allocated with `calloc` but never passed to `free`; close callbacks are no-ops, so every proxied connection leaks ~8.5KB.

The admin server authenticates with session cookies over plaintext HTTP (default port 8443, no TLS configured). The config struct declares an `https_port` field but no TLS is implemented anywhere. Session IDs travel in the clear, negating the strong credential generation (`/dev/urandom` + PBKDF2) done by `kernd init`.

SQLite is used from the libuv main thread (admin handlers) and from detached deploy pthreads, both calling `kern_db_exec_params` on the same `kern_db_t*`. Unless libkern's database layer opens with `SQLITE_OPEN_FULLMUTEX`, concurrent writes during a deploy could produce SQLITE_BUSY errors that propagate as silent failures.

The process manager's `kernd_process_reap` must be called explicitly, but the main loop never calls it on a timer or signal — exited children accumulate as zombies indefinitely.

Test coverage is solid for data-layer components (registry CRUD, process start/stop, vhost table, cgroup fallback, backup) but exercises zero network paths or integration flows.

<summary>Issues (7)</summary>

1. **Command injection in deploy worker** — `kernd_deploy.c` passes `app->repo_url` and `app->build_cmd` to `system()` with only single-quote wrapping. Escape embedded single quotes or use `execve` with an argv array.
2. **Command injection in backup** — `kernd_backup.c` passes `data_dir` and `app_name` to `system("tar ...")` with single-quote wrapping, same escaping gap.
3. **XSS in admin action URLs** — `kernd_admin_pages.c` interpolates `name` via `kern_buf_writef` into `<form action="/apps/%s/deploy">` without HTML-escaping, allowing stored XSS if an app name contains quotes or angle brackets.
4. **Proxy connection memory leak** — `proxy_conn_t` is `calloc`'d in `on_proxy_connection` but `proxy_conn_close` only calls `uv_close` on embedded handles; nobody calls `free(conn)`. Add a custom close callback that frees the struct.
5. **No TLS on admin port** — The admin server serves authentication pages and session cookies over plaintext. Add TLS termination or document that a reverse proxy (nginx) is required in front.
6. **SQLite thread-safety assumption** — The deploy worker's detached pthread writes to the same `kern_db_t*` concurrently with admin handlers on the main loop. Verify `kern_db_open` sets `SQLITE_OPEN_FULLMUTEX`, or add a mutex around registry writes.
7. **Proxy single-read truncation** — The proxy reads once into an 8KB buffer, forwards that, and stops reading from the client. Any request larger than 8KB (file uploads, large POST bodies) is silently truncated.

## Command injection via `system()` in deploy and backup

The deploy worker constructs shell commands by interpolating user-supplied strings:

```c
snprintf(cmd, sizeof(cmd),
         "cd '%s' && if [ -d .git ]; then git pull; "
         "else git clone '%s' -b '%s' .; fi",
         app_dir, app->repo_url, app->branch ? app->branch : "main");
int rc = system(cmd);
```

A `repo_url` value of `'; rm -rf / #` breaks out of the single-quote context. The `build_cmd` is similarly passed raw to `system()`. Since these values come from the admin web form (authenticated, but still user-controlled input), an operator typo or a compromised session can execute arbitrary code as the daemon user. The backup module has the same issue with its tar command.

The fix is either to escape single quotes (`'` → `'\''`) in all interpolated strings before `system()`, or preferably to use `fork()/execvp()` with an explicit argv array that avoids shell parsing entirely.

## Stored XSS in app action forms

In `kernd_admin_pages.c`, app names are rendered into form action URLs using `kern_buf_writef`:

```c
kern_buf_writef(body,
    "<form method=\"POST\" action=\"/apps/%s/deploy\" style=\"display:inline\">"
    "<button class=\"btn btn-primary btn-sm\">Deploy</button></form> ",
    name ? name : "");
```

The `name` value comes from the database without HTML escaping. An app registered with a name like `"><script>alert(1)</script><x x="` would inject markup into the page. The cell contents elsewhere use `kernd_html_escape`, but these URL attributes do not. Apply URL-encoding or at minimum HTML-escape the name in the action attribute.

## Proxy `proxy_conn_t` memory leak

Each accepted connection allocates a `proxy_conn_t` (8KB+ embedded buffer) via `calloc`. The `proxy_conn_close` function calls `uv_close` on the embedded `client` and `backend` handles, but the close callback is a no-op:

```c
static void on_close(uv_handle_t *handle) {
    (void)handle;
    /* Freed by proxy_conn_close */
}
```

Nobody ever calls `free(conn)`. Since the struct contains two `uv_tcp_t` handles that close asynchronously, the correct fix is to track close completions (e.g., a ref count decremented in the close callback) and call `free(conn)` when both handles are closed.

Additionally, `send_error_response` writes from a stack-allocated `char response[512]` buffer via `uv_write`. If libuv queues the write rather than completing it inline, the write could read stale stack memory. In practice libuv copies data for queued writes on most platforms, but this is fragile — a heap-allocated response buffer eliminates the risk.

## Proxy request handling: single-read truncation

The proxy reads from the client exactly once (`uv_read_start` → `on_client_read` → `uv_read_stop`), buffers up to 8KB, then connects to the backend and forwards that single buffer. Requests larger than 8KB are silently truncated — the proxy never resumes reading from the client. This is a data-correctness bug for any proxied app that accepts form submissions or file uploads larger than 8KB.

## Zombie accumulation without SIGCHLD integration

The process manager's `kernd_process_reap` function iterates the process table and calls `waitpid(WNOHANG)` on each tracked PID. However, nothing in the main event loop triggers this function — there's no `uv_signal_t` watcher for SIGCHLD and no periodic timer. Exited children accumulate as zombies until an operator restarts the daemon. Wire up a `uv_signal_t` for SIGCHLD that calls `kernd_process_reap`, or add a periodic timer.

## Test coverage gaps

Not tested:

- Admin HTTP handlers (session flow, auth redirect, form submission)
- Deploy worker thread lifecycle (clone, build, status transitions, concurrent SQLite access)
- Proxy network behavior (connection acceptance, Host header parsing, backend forwarding, error responses)
- Log capture pipe reading and rotation trigger
- Graceful shutdown sequence (signal → uv_stop → drain close callbacks)
